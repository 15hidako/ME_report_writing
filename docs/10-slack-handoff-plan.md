# Slack経由の回答引き継ぎ実装計画

更新日：2026-11-03

状態：初版の実装と検証は完了。通常のPC環境への取り込みと実記事での運用確認は、[現在の作業状況](00-project-plan.md#現在の作業状況2026-11-03)で追跡する。

## 目的と構成

スマートフォンのPWAからSlackへ回答を渡す際、保存したJSONを探し直す手間を省く。既存のPWA内で回答ファイルを生成し、スマートフォンの共有画面へ直接渡す。

初版の推奨案は、「保存して共有」を押し、共有先としてSlackと専用の非公開チャネルを選んで送る方式とする。共有先の選択と送信操作は残る。この操作を許容する案であり、特定チャネルへの完全なワンタップ送信とは区別する。

```text
スマホで回答 → 保存して共有 → Slackで宛先を選んで送信
PCのSlackで添付を取得 → 既存アプリへ追加で取り込む → 記事作成と手動投稿
```

GitHub Pages、TypeScript、Vite、既存のlocalStorage保存を維持する。新しいサーバー、クラウドDB、ログイン基盤、Slack Botは初版に追加しない。回答は端末とSlackに置き、長期保管はPCのリポジトリ外や自分のGoogle Driveで行う。

## 実装対象

### 保存と共有

1. 入力画面に保存して共有を追加する。既存の保存だけを行う操作も残す。
2. ボタンを押したら入力を検証し、現在の回答を端末に保存する。保存失敗時は共有を始めず、入力を保持する。
3. 保存した回答1件を既存のJSON配列形式にして、メモリ上でファイルを生成する。全回答を添付しない。
4. 生成したファイルをWeb Share APIでスマホの共有画面へ渡す。利用者がファイル選択画面から探す手順を挟まない。
5. キャンセルや共有失敗後も回答を保存済みのまま残し、同じ回答を再共有できるようにする。

共有画面はボタン操作に続けて開く。ファイル生成の前に通信や長い非同期処理を挟まない。`navigator.canShare`でファイルの共有可否を確認するが、その結果だけでSlack側の受信対応までは保証しない。[Web Share仕様](https://www.w3.org/TR/web-share/)

Slackへの投稿完了をPWAから確認できるという前提は置かない。共有画面への引き渡し後に送信済みと断定せず、投稿の確認はSlackで行う。送信台帳、自動再送、送信待ちキューは作らない。

### PCでの追加取り込み

既存のJSON読込は全件置換のため、引き継ぎ用に回答1件を追加・更新する操作を設ける。PCではSlackから添付を取得して取り込む。Slack APIによる自動取得は初版に含めない。

| 取り込む回答 | 処理 |
|---|---|
| 未登録のID | 既存の回答を残して追加する。通し番号が重複した場合は新番号を提示し、確認後に割り当てる。IDは変えない。 |
| 同じIDで回答内容も同じ | 重複追加せず、何も変更しない。 |
| 同じIDで回答内容が異なる | 更新前に差分と確認を表示する。PC側の通し番号と登録済み投稿URLを保つ。時刻だけで自動上書きしない。 |
| 不正なJSONや欠けた再訪参照 | 既存データを変更せず、理由を表示する。初回への参照は固定IDで確認する。 |

既存の検証と上書き前バックアップを使う。現在の全件JSONによるバックアップ保存・復元も維持する。新たな版管理方式や別の保存基盤は導入しない。

## 実装順序と検証

| 順序 | 対象 | 完了条件 |
|---|---|---|
| 1 | スマホ実機で共有を試す | 合成回答1件をPWA内で生成し、ファイルを探さずSlackへ添付できる。PCで取得し、内容を読める。 |
| 2 | 保存して共有 | 入力検証、端末保存、1件の共有がつながる。共有のキャンセルや失敗後も回答が残る。 |
| 3 | PCでの追加取り込み | 他の回答を消さず、同じIDの再取り込みと更新を扱える。投稿URL、通し番号、再訪参照を守る。 |
| 4 | 回帰確認 | `npm test`と`npm run build`が通る。PC幅とスマホ幅で操作できる。 |

最初にJSON添付の実機対応を確認する。JSONが共有先で扱えない場合は、中身を同じJSONにしたテキストファイルで試す。その場合はPC側のファイル受付も対応させる。どちらも成立しない端末では既存のJSON保存を残し、共有方式を決め直す。成立を確認する前に周辺機能を増やさない。

実装ファイルは主に`src/main.ts`、`src/ui/form.ts`、`src/storage.ts`と関連テスト。共有処理は必要なら小さな専用モジュールに分ける。既存の`VisitRecord`と検証処理を再利用する。

共有内容が1件だけであること、保存失敗時に共有しないこと、キャンセル後の保持、二重取り込み、更新確認、通し番号の重複、不正ファイルを重点的に検証する。実データや認証情報をテスト、スクリーンショット、GitHubへ入れない。

## 完全なワンタップ送信が必要になった場合

PWAから固定のSlackチャネルへ直接送る場合は、Slackの秘密キーを扱う中継APIが必要になる。その場合でも、最初からクラウドDB、PWAの配信先変更、PCの自動受信まで加える必要はない。既存の実行環境を使えるか確認し、送信先を固定した認証付きAPIを1つ用意する案から検討する。秘密キーを公開JavaScriptへ埋め込まない。[SlackのWebhookと秘密情報](https://docs.slack.dev/messaging/sending-messages-using-incoming-webhooks/)

共有先を選ぶ操作が実際に負担かどうかを見て、直接送信へ進むか判断する。今回の見直しでは完全ワンタップの要件を確定し直したわけではなく、依存を増やさず目的を満たす初版の案を提示している。

## 別に扱う改善

未完成入力の自動保存と復元は便利だが、今回の共有操作の短縮には必須ではないため、別の改善として扱う。オフライン起動対応、双方向同期、Google Drive API連携、記事の自動投稿も初版に含めない。

Slackは受け渡し先として使い、回答の長期保管先をPCやDriveにも用意する。無料プランの履歴とファイルには閲覧期間と保持期間の制限がある。[Slackの保持制限](https://slack.com/help/articles/115002422943-Usage-limits-for-free-workspaces)

既存画面の配置を活かし、説明や補助ラベルを増やさず、保存と共有の操作を分かりやすくする。公開、Slackチャネル作成、実回答の送信は、2026-11-02の計画見直し時点では実施していなかった。実装後の確認範囲は下記に記録する。

## 実施結果（2026-11-03）

- 「保存して共有」と「回答を追加読込」は実装・公開済み。保存失敗時には共有を始めず、キャンセルや共有失敗後も回答を保持する。
- スマホからSlackへの1件JSON共有とPCでの取得を確認した。
- 独立した検証用ブラウザで、追加読込、同じ回答の重複防止、プロンプト出力、JSON再保存を確認した。更新差分、通し番号と投稿URLの保持、欠けた再訪参照の拒否も回帰テストで確認している。
- 実機確認専用の画面、合成回答生成処理、その専用テストは撤去し、公開版へ反映済み。

これらは共有機能の実装確認であり、実記事の作成や手動投稿の完了を意味しない。テスト回答を実際の体験として使わず、本人の回答を本人が推敲して投稿する。
