### WP-1 投稿URLだけを安全に更新する

**対象**: `src/storage.ts`、`src/main.ts` の `savePostedUrl`、`src/board/main.ts` の `moveCard`、対応する保存・画面テスト。

現在はダイアログを開いた時点の回答を保持し、決定時に回答全体を `VisitStore.save` へ渡している。`save` は新規追加も行うため、更新の巻き戻しと削除済み回答の復活が起こる。

**修正方針**

- 既存回答の投稿URLだけを変更する処理を保存層に設け、両画面から使う。汎用の任意フィールド更新APIへ広げる必要はない。
- 決定時点の回答を読み、存在しなければ拒否する。最新の評価やメモ、料金、通し番号などを保持したうえで、投稿URLと必要な更新日時だけを変える。
- ダイアログ表示時の投稿URLも渡し、そのURLが別画面で変更されていた場合は競合として拒否する。無関係な回答項目の変更は保持して進められるようにする。
- `VisitStore.save` の新規追加機能は維持する。全呼び出しを一律に更新専用へ変えない。
- 投稿済みから戻す操作とまとめカードの投稿URL操作にも、古いオブジェクトを保存する同種の経路がないか確認する。まとめを削除したあとにダイアログの決定で復活させない。
- 失敗時は入力値を残して理由を表示し、投稿済みの段階に進めない。現在のバックアップと復旧の仕組みを利用する。

**必須テスト**

1. URLダイアログ表示後に別画面で回答のメモや料金を変更しても、その値が残る。
2. 表示後に回答を削除すると保存を拒否し、回答が復活しない。
3. 表示後に別画面で投稿URLを変更すると競合を知らせ、新しいURLを上書きしない。
4. 正常なURL登録、入力画面での空欄による解除、ボードでの投稿済み解除が維持される。
5. 通常の新規保存、既存回答の編集、保存失敗時のバックアップが従来どおり動く。

1〜3は保存層のテストだけで済ませず、入力画面とボードの配線も検証する。localStorage全体に対する真に同時の書き込みまで原子的になったと説明しない。今回まず防ぐのは、ダイアログ中に古くなった回答による上書きである。

### WP-2 週次確認用ファイルの競合を防ぐ

**対象**: `scripts/local-data.mjs` の `writeCheckFile` と週次確認の実行経路、`scripts/local-data.test.mjs`。必要な場合のみ `src/board/main.ts` の `sync`。

`targets.json.tmp` などの固定名を複数の書き込みが共有している。一時ファイルを使っていても、その一時ファイルへの書き込み自体が衝突する。

**修正方針**

- 保存要求ごとに一意の一時ファイルを作り、同じ保存先への要求を直列化する。UUIDや既存の原稿保存処理のパターンを参考にし、新しい依存を追加しない。
- JSON検証は置換より前に行う。失敗した要求で保存先を途中の内容にしない。一時ファイルは成功・失敗のどちらでも片付ける。
- 一時ファイルは対象と同じディレクトリに作り、完成後に置き換える。パス制限、書けるファイルの限定、リクエストの信頼性チェックは維持する。
- 直列化待ちの前の要求が失敗しても、後続の要求まで永久に失敗・待機しないようにする。
- `sync` は対象の書き出し→実行→結果取得→バックアップ保存の複数要求である。複数タブが実行した場合に、実行中の確認対象を別要求が差し替えないことも検証する。必要なら実行中の `targets.json` 更新をサーバーで拒否し、利用者へ競合を伝える。
- 防げる範囲を明示する。単一サーバープロセス内の排他を、別プロセスや外部エディタも含むロックとして説明しない。

**必須テスト**

1. 長さの異なるJSONを同じ保存先へ同時に送っても、保存結果が必ずどちらか1件の完全なJSONになる。
2. 要求ごとの成功・失敗が定めた直列化の規則と一致し、混ざった本文を成功扱いしない。
3. 不正JSON、書き込み失敗、置換失敗の後も旧ファイルを読め、次の正常な保存が進む。
4. 別ファイルへの書き込みは、それぞれ正しく完了する。
5. 週次確認中の別タブからの対象更新と実行要求を処理し、対象と結果が無言で入れ替わらない。

偶然のタイミングに依存する反復だけを回帰テストにしない。実ファイルでの並列確認に加え、必要な箇所だけ処理の完了を制御して競合を再現する。テスト用の汎用I/O基盤を新設しない。

### WP-3 回答の内容差分を日時だけで捨てない

**対象**: `src/board/answer-sync.ts`、`src/board/answer-sync.test.ts`、必要に応じて `src/board/main.ts` と取り込みの画面テスト。既存の `src/handoff-import.ts` の比較規則を利用する。

`updatedAt` には回答本文の更新とPC側の投稿URL更新が混在する。この日時だけでは、どちらの回答内容が最新かは決められない。

**修正方針**

- 現在の回答との実質的な差分を、`prepareHandoffImport` の既存規則で先に確認する。通し番号、投稿URL、日時などの管理情報だけの違いで取り込みを繰り返さない。
- 内容が同じなら通知も取り込みもしない。
- 内容が異なりファイル側が新しい場合は、既存の差分確認へ進める。既存回答の更新を自動確定しない。
- 内容が異なりファイル側が同時刻または古い場合も、無言で除外しない。最小の対応として、既存のエラー表示に競合とファイル名を出し、履歴の「回答を追加読込」で差分確認できることを案内する。古いファイルを自動適用してPCの訂正を戻さない。
- 同時刻で異なる複数ファイルがある場合は、既存の曖昧さの通知を維持する。最新ファイルを選ぶ既存規則と、PC保存値との照合を混同しない。
- 新しい永続フィールドや既読台帳は今回の必須条件にしない。更新日時の意味を変えて問題を隠すこともしない。

**必須テスト**

1. スマホで11時に本文訂正、PCで12時に投稿URL登録という順でも、内容差分の存在が利用者に伝わる。
2. 同一日時で本文が異なる場合、無言で捨てない。
3. 本文が同じでPCの通し番号、投稿URL、日時だけが違う場合は、新着や競合にしない。
4. PCの本文が新しく古い回答ファイルと異なる場合、PC内容を自動で戻さない。
5. 新規回答、再訪元が先に必要な回答、同時刻の重複ファイル、差分確認中の外部更新を従来どおり扱う。

既存の「ボードより古い回答は返さない」テストは、候補を自動追加しない性質を保ちつつ、内容差分があれば通知することも確かめる。

### WP-4 別ページの出勤判定を慎重にする

**対象**: `src/checks/judge.ts` と `src/checks/judge.test.ts`。必要な場合のみ表示状態との接続テスト。

別ページの出勤表では、本文全体に名前が含まれるだけで `listed`、含まれなければ `not_listed` にしている。名前だけでは現在の勤務予定を判断できない。

**修正方針**

- `listed` は対象者と確認対象期間の勤務時間の対応を確認できた場合に限る。
- 対象者や期間を特定できないページ、常設ナビしか根拠がないページ、想定外の転送先は `unknown` にする。取得成功や名前の欠落だけで出勤なしと断定しない。
- `not_listed` は、対象期間の出勤表を十分に読めて、対象者に勤務予定がないと判断できる場合に限る。一日だけ休みでも、7日間すべて休みと扱わない。
- サイトごとの構造が不明なら、別ページ経路を `unknown` として要目視へ回す対応を先に完成させてよい。対応サイトを推測した巨大な正規表現や、ブラウザ自動操作基盤を追加しない。
- プロフィールページで日付と時刻を読む既存の正常系は維持する。在籍404/410、取得失敗、文字コード処理も維持する。

**必須テスト**

- 対象者名の後ろに休みと書かれたページを出勤ありにしない。
- ナビに対象者、出勤欄に別の人がいるページを出勤ありにしない。
- 過去年、期間外の日付、似た名前の別人を対象者の現在の勤務とみなさない。
- 日付や勤務時間が読めないページは `unknown` になり、ボードで要目視の対象になる。
- 既存プロフィール経路の正しい勤務時間、休み、年末年始、HTTPエラーを維持する。

合成HTMLだけで対応サイト全般の精度が保証されたと報告しない。

### WP-5 無料カタログと有料記事の規則を分ける

**対象**: `src/prompt/style-profile.ts`、`src/prompt/build-prompt.ts` と対応テスト。

共通のヘッダーが、有料記事専用の指示まで無料カタログへ追加している。

**修正方針**

- 共通の事実・禁止事項と、記事種類ごとの公開範囲・構成規則を分ける。引数や分岐は現在存在する記事種類に必要な範囲に限定する。
- 無料カタログでは、同じ都道府県の本人の投稿済み記事へリンクできるようにする。店名・源氏名や年齢などを伏せる既存要件は維持する。
- 無料カタログに、その記事自身の有料欄や有料欄末尾を前提とした指示を入れない。リンク先の有料体験談へ誘導する用途は維持する。
- 店やセラピストのプロフィールリンクと、本人が投稿した記事へのリンクを明確に区別する。再訪記事の無料部に置く初回記事リンクも共通規則で禁止しない。
- 単体・再訪の通常版と名前公開版、まとめ、PCの素の文章、公開版HTMLの規則を保つ。タグ上限、通し番号の非公開、販売実績の禁止、`span style`、評価6軸を落とさない。
- プロンプト全体の言い換えや文体変更は行わない。矛盾を解消する箇所だけを変更する。

**必須テスト**

1. カタログが無料記事1本を要求し、本人の投稿済み記事リンクを許可する。
2. カタログに、有料欄を持つ前提の必須指示が含まれない。
3. カタログでも非公開情報の制限が残る。
4. 再訪記事の初回リンクが無料部に置ける一方、通常版の店舗プロフィールリンクは有料部に残る。
5. 単体、再訪、まとめの正常系と、PC版・公開版の出力形式が維持される。

従来の矛盾する文言そのものを期待するテストは、目的を保った振る舞いのテストへ書き換える。テストを消して成功扱いにしない。

### WP-6 不正URLをAPI境界で処理する

**対象**: `scripts/local-data.mjs` の `createHandler` と `scripts/local-data.test.mjs`。

ルートの `decodeURIComponent` が `try` の外にあり、不正なパーセントエンコードでPromiseがrejectする。

- URLとルートの解析をエラー処理の範囲に入れ、不正なエンコードはHTTP 400で返す。
- API外の要求を次のミドルウェアへ渡す動作と、信頼できない要求を403で拒否する動作を保つ。
- JSONの構文エラー、存在しないファイル、競合、予期しないI/O失敗の区別を維持する。
- `%ZZ` や途中で切れたUTF-8エンコードで、応答が完了し未処理の例外が漏れないことを確かめる。正常な日本語フォルダ名や既存のパス逸脱拒否も検証する。

関数単体のテストに加え、可能なら合成データ用のハンドラーをHTTP経由で1回通す。本人の `data/` をルートに使わない。

### WP-7 投稿済みURLの境界を確かめる

**対象**: `src/prompt/publication.ts`、対応テスト、必要なら `src/record-validation.ts` と保存済み値の読み込み経路。

現在はwakustドメインのルート以外を記事とみなす。具体的な記事パスの形式は監査で確認していないため、推測した許可パターンを実装しない。

**進め方**

1. 現在の公開された記事URL形式を、公式ページまたは公開記事で確かめる。確認日と根拠URLを完了報告に残す。本人の実回答や非公開原稿は使わない。
2. 正常な記事URLと、プロフィール・カテゴリー・規約等の非記事URLを区別するテストを作る。存在確認のための通信を保存操作へ追加しない。
3. ホスト名、資格情報、クエリ、フラグメント、末尾スラッシュなどの既存条件を確認し、正常URLを不用意に拒否しない。
4. 判定を厳格にした結果、過去に保存できたURLのために回答全体やボード全体が読み込めなくならないようにする。入力時の検証、保存済み値の保持、投稿済み判定を分ける必要があるか確認する。旧URLを勝手に削除・正規化しない。
5. 記事形式の根拠が不足する場合は、このWPだけ未完として残し、他の修正を完了させる。根拠のない正規表現を追加して済ませない。

投稿済み人数、まとめ解禁、カタログ対象にも判定が使われるため、非記事URLをこれらの対象に数えないことと、正しい既存記事の扱いを合わせて検証する。

## 6. 今回行うリファクタ

WP-1の投稿URL更新、WP-2のファイル保存、WP-5の記事種類別の規則を、それぞれ必要な責務としてまとめる。UI側に同じ競合判定や保存規則を複製しない。

`src/main.ts` と `src/board/main.ts` の全面分割は今回の完了条件に含めない。バグ修正の過程で処理を切り出す場合も、公開する関数を増やしすぎず、元の呼び出し経路をテストできる単位にする。新しい設定、汎用ワークフロー、互換レイヤー、未使用の拡張点は足さない。

## 7. 検証とレビュー

各WPでは、まず対象の回帰テストが現在のコードで失敗することを確認してから修正する。続いて関連テストを実行する。機械的な整理だけの部分に、実装のコピーのようなテストを増やさない。

全WPを統合したあと、次を実行する。

```text
npm test
npm run build
git diff --check
git status --short
```

追加依存は原則不要である。依存やlockfileを変更した場合は、その理由を明記し、PJで定めた監査も行う。

画面確認は合成データ専用の5183番、または保存領域を隔離したブラウザで行う。最低限、入力画面とボードの投稿URL操作、取り込み競合の表示、週次確認の成功と失敗を確かめる。画面を変更した場合は、入力画面375px・1280px、ボード1280pxで操作と表示を確認する。

テスト補助でViteを直接起動する場合、既定の依存探索で `data/articles` 内のHTMLを走査させない。検証用の設定では `optimizeDeps.noDiscovery: true` と `entries: []` などで探索範囲を限定する。本番設定を無関係に変更しない。

コードレビューでは、以下を重点的に見る。

- 古い回答の全体保存が、修正した経路に残っていないか。
- 途中失敗を成功として返していないか。ロックや一時ファイルが残らないか。
- 古い回答の自動上書きや、取り込みの繰り返しを新たに起こしていないか。
- `unknown` を誤って正常扱いし、確認対象から外していないか。
- プロンプトの修正で、本文の材料や公開範囲の要件を落としていないか。
- URL検証の変更で旧データの読み込みと復旧を壊していないか。

既存テストの成功だけを理由に、未実行の画面操作や外部サイトでの確認まで完了としない。修正後に別の問題を発見した場合は、現在の変更に起因するものを直し、無関係な問題は報告にとどめる。

## 8. 実装完了時の報告

次の内容を簡潔に報告する。

1. 各WPの完了・未完と、変更した挙動。
2. 修正したファイル、追加または書き換えた回帰テスト、再現結果。
3. 全テスト、本番ビルド、画面確認、差分レビューの結果。
4. 実サイトのURL形式などの確認根拠と、確認できなかった事項。
5. 保存形式の互換性、排他処理の保証範囲、残る制限。UI委任を行った場合は委任先と実施結果。

コミットとpushは、この実装指示からは行わない。別途明示された場合だけ、所定の確認と承認手順に従う。
