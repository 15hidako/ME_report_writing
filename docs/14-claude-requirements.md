# Claude Code由来の原要件

移植日：2026-11-06

Claude Codeで決めた案を、他のエージェントも参照できるように移した文書である。元の設計書はそのまま残す。この文書は原案を作り直すための仕様書ではない。

ユーザーは2026-11-06に、過去の案を崩さず、Claude Codeに残るものを原則として扱うよう明示した。後の実装や引き継ぎに違いがあっても、それを根拠に元の要件を縮めない。出典ID、採用の経緯、後の資料との差異は [判断履歴](15-requirements-history.md) に記録した。

## 1. 目的と作業経路

個人の訪問後の記録を、販売プラットフォームへ投稿できる記事に成型する。本人のiPhone、iPad、Laptopで使う。質問票は訪問直後に片手で入力し、約5分以内に終えられることを目指す。5分は設計目標であり、実測済みの結果ではない。

元の経路は、PWAへ入力、端末内へ保存、生成プロンプトをコピー、ClaudeのアプリまたはWebへ本人が貼り付け、記事を推敲、投稿フォームへ本文を貼り付けて画像を添付、という流れである。アプリから生成APIを呼ぶ構成や自動投稿は採用していない。他のエージェントが執筆を引き継ぐ場合も、この手動投稿とデータの扱いを守る。

出典：CC-01、CC-02、CC-06、[元の計画](00-project-plan.md#全体フロー)。

## 2. 投稿用の出力

| 出力 | 元の用途と確認点 |
|---|---|
| タイトル | シリーズ名・番号を含めたフック型。人物像など、記録にある属性を使う。店名・担当者名は入れない |
| タグ | 半角コンマ区切り。エリア、都道府県、系統、特記など、本文と記録に沿う語を選ぶ |

| 販売ポイント案 | 個別の販売価格を本人が決めるための案。保存値や初期値を承認済み価格とみなさない |
| サムネイルPNG | 投稿画面のトップ画像として別途添付する |

2026-11-10追記：投稿先のタグは最大6個で、都道府県名と「メンエス」は入力できない。販売部数や売上などの販売実績は、タイトルにも本文にも入れない。経緯は差異 [H-07](15-requirements-history.md#h-07-タグの個数とngタグ) と [H-09](15-requirements-history.md#h-09-販売実績の文言) にある。

生成プロンプトはタイトル、タグ、無料部分HTML、有料部分HTMLの4ブロックを求める。元の計画には販売ポイント案とサムネイル作成の経路もある。4ブロックだけを見て、残りの依頼を落とさない。

HTMLは本文の見出し、強調、色、改行などを指定する形式である。ユーザーが提示した元のサンプルには、`span`の`style`属性による文字色と太字の指定もあった。独立したHTMLファイルの作成が当初の必須条件だったわけではない。ファイル保存やプレビューは依頼に応じた補助物であり、投稿本文の装飾をプレビュー専用CSSへ移して済ませない。

元のテンプレートが挙げるタグは、`h3`、`p`、`ul`、`li`、`a`、`strong`、`em`、`small`、`span style`、`br`である。使用する装飾は投稿本文に含め、投稿先での対応を確認する。現行プロンプトから`span style`が抜けている点は、原要件を取り消す根拠ではない。具体的な色や余白を新しい標準として固定する変更は、今回行っていない。

出典：CC-03、CC-04、[記事テンプレート](02-article-templates.md)、[現行出力形式](../src/prompt/build-prompt.ts)、差異H-01。

## 3. アンケートから本文への反映

元の設計は、評価6軸と段階別の記録を記事構成へ対応させるものだった。短文、短い段落、細かな改行は読み方の指定であり、記事全体の情報量を減らす指定ではない。2026-11-06のユーザー指示でも、勝手な要約とアンケート内容の省略が否定された。

原本と照合し、記入済みの材料を判断なしに削らない。重複表現を整理する場合も、評価、理由、条件、留保、出来事の違いは保つ。内部管理用の項目まで本文に逐語掲載するという意味ではない。

| 質問票 | 本文・投稿情報へ引き継ぐもの | 区別するもの |
|---|---|---|
| A：基本情報 | 訪問日、地域、店名・担当者名とURL、年齢と推定の別、コース、料金、オプション体系・選択内容、部屋タイプ | 部屋タイプと建物名・階数・部屋番号。予約方法や証跡保存チェックなどの管理情報は、自動的に本文へ載せない |
| B：評価 | 顔、スタイル、接客、マッサージ技術、エロ施術、寛容度の6軸と各コメント | 好印象だけを取り出さず、低い評価と理由も残す。2軸などへの縮小を既定にしない |
| C：人物像 | 系統、体型、カップと実感、特記。タグ候補となる語も確認する | 観察した印象と、性格・実年齢などの事実。未知の値を推測で置き換えない |
| D：施術の記録 | 対面、うつ伏せ前半、オイル以降、仰向け、終盤、その後の各段階。最も良かった場面と残念だった点 | チップの選択順と実際の出来事の順序。未選択と「なかった」は別 |
| E：言葉と総評 | 実際に記録したセリフ、心の声、タイトル用の材料、リピート意向 | 話題と直接引用。未記録の言葉、感情、再訪希望を補わない |
| F：販売情報 | 記事タイプ、シリーズ番号、販売ポイント案 | 保存値と本人が確定した販売設定 |

`serializeRecord`は記事向けの材料を出す処理であり、原本の全項目を複写する処理ではない。時間帯、予約方法、証跡チェックなどは出力されず、自由タグと販売ポイントは別の経路で渡される。プロンプトに見当たらないという理由だけで、原本にもないと判断しない。

記録が薄い箇所では、事実を創作して長さを埋めない。元の改善方針も、薄い箇所を知らせて材料の追記を求めるものだった。扱えない内容がある場合は、その範囲と理由を示す。説明せずに記事の種類や構成を変え、短い別稿を完成品として扱わない。

出典：CC-04、CC-05、CC-07、U-01、[質問票](01-questionnaire.md)、[材料出力](../src/prompt/serialize.ts)。

## 4. 構成と文体

### 単体体験談

無料部は、導入、人物像、お勧め対象、対面から施術前半、有料部に何を載せるかの説明、注意書きという構成である。有料部は、店舗と担当者の情報、評価6軸、後半の段階別記録、総評という構成を引き継ぐ。元の具体的な見出しと無料・有料の切り位置は [記事テンプレート](02-article-templates.md#1-単体体験談本体) に残っている。

店名、担当者名、関連リンクは、単体体験談と再訪記事では有料部に置く。元のユーザーサンプルでは無料部にあったが、その後の販売型への変更案を採用している。タイトルにも店名と担当者名を出さない。有料部はリンク先を開かなくても内容が分かる本文にし、URL文字列も併記する。

元の改善では、お勧め対象に挙げる評価軸を★5に限るとしている。該当軸がないときに星や評価を上げて埋めない。段階別の記録を極端に薄くせず、最後の総評にはリピート意向と残念な点も含める。

### 文体

ユーザーは過去の自作記事のトーンを踏襲することを認め、改善意見を求めた。元の [文体プロファイル](03-style-profile.md) と隠語辞書を参照する。です・ます調と体言止め、短文、1段落2〜3文を目安とする改行、正直な減点、控えめな記号、元の締め方を保つ。一般的な文章整理の都合だけで、原案の声や情報を削らない。

セリフと心の声の往復は、記録された材料がある場合の構成である。回数を埋めるための創作はしない。隠語の説明は初出で推測しにくいものに限り、すべてに括弧説明を付けて解説記事に変えない。見出しの未置換部分や「…」だけの仮見出しを残さない。

### 派生記事

| 種類 | 元の方針 |
|---|---|
| 無料カタログ | 自分の投稿済み記事への案内。単体記事の代替にしない |
| まとめ記事 | 原計画は個別体験談6本の投稿後。過去の販売内容を含む旨と元記事のリンクを記載する。後続実装の「投稿済みの異なる担当者6人」との関係は差異H-06を参照 |
| 再訪記事 | 初回記事へリンクし、今回との差分を扱う。前回の言葉や出来事を今回の事実にしない |
| ノウハウ記事 | 訪問回数を増やさず作れる別種の記事。個別体験談の本数を満たすための代用にはしない |

2026-11-10追記：無料カタログは既存記事の編集で更新する([H-08](15-requirements-history.md#h-08-カタログ無料記事の更新方法))。同じ訪問を、切り位置だけ変えた別記事として出さない([H-10](15-requirements-history.md#h-10-同じ訪問の再構成))。再訪記事にも店舗名と担当者名を有料部に書く。

まとめ記事での要約や、再訪記事の差分中心の構成を、単体体験談を短縮する根拠にしない。1アカウントで無料の案内と有料記事を運用する方針であり、同じ内容を複数アカウントへ展開する案は採用していない。

出典：CC-05、CC-06、CC-07、[計画](00-project-plan.md)、[構成と文体](03-style-profile.md)、[記事生成](../src/prompt/build-prompt.ts)。

## 5. 事実と料金

- 質問票にない体験、引用、感情、因果、時間差を作らない。印象を客観的な事実へ強めない。
- 提案、説明、選択、支払い、実施を別の出来事として扱う。候補語を選んだだけで、追加料金を払った、希望が実現した、という事実を補わない。
- 旧記録の保存順から押下順を復元しない。新しい記録の選択順も、実際の施術順や時刻とは同一視しない。
- 料金の未確認と0円を区別する。メニューの設定価格、選択内容、実際の支払額を混同しない。原本と後からの本人確認が異なるときは、最新の明示確認を使い、原本自体は書き換えない。
- 確定値の足し引きと、不明な支払額の推定を区別する。ユーザーが確認済みの金額による計算を認めている場合は、根拠を保って計算できる。同じ料金の再質問をしない。
- 訪問時の支払額は記事の販売価格ではない。元計画の100〜300ptなどは価格戦略の案であり、個別記事の確定価格ではない。

出典：CC-07、U-01、G-05、G-06、G-07、G-08、G-10、[質問票](01-questionnaire.md)、[観察語の意味の条件](07-questionnaire-next-options.md#保存先と意味の条件)。

## 6. サムネイル

サムネイル生成は、ユーザーが追加した必須の作成経路である。元の設計は、シリーズを認識できる統一デザインに、エリア・人物像・記事のフックなどの文字を差し替えるCanvas方式で、PNGを保存して投稿画面へ添付する。AIによる人物写真の生成を前提にはしていない。

文字なしにするという途中の発言は、直後にアプリアイコンの話だと訂正されている。サムネイルの文字をなくす要件として採用しない。

既存実装は4配色、1200×675である。これを元の実装として保ち、現在の投稿先の画像規格と差があれば説明する。投稿先の規格確認だけで元のシリーズデザインまで変更した扱いにしない。今回不採用になって削除した画像は、新しいデザイン基準にしない。

2026-11-10追記：投稿先のサムネイルは縦横比2:3と確認できたため、本人の指示で出力を1000×1500の縦長に変えた。4配色、文字中心のシリーズデザイン、PNG保存の経路は元のまま。長いエリア名やフックは折り返して収める。それでも収まらない分は末尾を「…」にして打ち切る。上の1200×675は変更前の記録として読む。

出典：CC-03、CC-04、CC-08、[既存実装](../src/thumbnail.ts)、差異H-03。

## 8. 原本と公開範囲

実回答、原稿、訪問先や担当者を特定できる情報、確認画像はリポジトリ外で扱う。この移植にも、実回答JSON、過去の投稿本文、チャット全文は含めていない。

元の運用で本人がClaudeへ貼り付けることと、エージェントが別のAIや外部サービスへ実回答を送ることは別である。後者を自動的に許可済みとしない。日本語の仕上げでも、外部送信禁止の資料は渡さない。

料金や記事対象について本人が確定した内容は、その確認資料を参照する。別のPCに私的資料がない場合は、確定値を再推定したり、公開リポジトリから復元したりしない。必要な資料の所在を確認する。

## 9. 作業の区切り

要件の移植、記事の作成、本人による確認、手動投稿、投稿URLの登録は別の到達点である。文書を移植したことや、ファイルを作れたことだけで記事やM2を完了扱いにしない。

記事作業では、元の構成と原本の材料が保たれていること、未記録の内容が増えていないこと、投稿欄へ貼るHTMLに必要な装飾があること、本人に残る判断を確認する。アプリ作業では、その変更に対応するテストと`npm run build`を実施する。文書のみの変更を理由にアプリ改修や依存更新を始めない。

通常PCへの取り込み、実記事での通し確認、実入力時間、iPhone実機の操作・読み上げ評価は [残件一覧](11-remaining-tasks.md) を参照する。過去のテスト件数やモバイル幅の確認を、今回の実機確認結果へ読み替えない。
