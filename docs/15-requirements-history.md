## 出典の扱い

1. ユーザーの明示発言と、その後に了承された案を確認する。エージェントの提案だけの記述とは分ける。
2. Claude Codeで成立した案を原則とし、対応する元の設計書を読む。元案を変える場合は、ユーザーが明示した変更とその対象を確認する。
3. 後のコードは実装の証拠として扱う。コードにない、許可タグから落ちている、といった事情だけで原要件を取り消さない。
4. 後の要約、下書き、引き継ぎに範囲の縮小があれば、差異として残す。単に日付が新しいという理由では原案を上書きしない。

実行環境の安全上の制約や、現在のユーザーが明示する公開・外部送信の境界は守る。制約によって扱えない範囲は説明し、原案そのものが変更されたことにしない。

差異：2026-11-13、本人がボードで記事5(体験内容起点)の原稿を直した。生成時の原稿と比べると、言い回しの手直しに加えて次の型の部分が変わっていた。無料部分の評価6軸で「エロ施術」を「過激施術」に変え、特記を系統の行にまとめて料金の合計の行を足した。出勤確認は「11月中旬」「確認済」と書き、総評からはリピート意向の一文を削って残念な点の記述を減らした。本人は、型の部分の変更を今後の記事でもそろえ、言い回しの手直しは文体の調整に使うと決めた。

今回の処置：本人が選んだ3点を、生成プロンプト `src/prompt/build-prompt.ts` と記事テンプレートに反映した。記事全体(無料部分・有料部分・カタログ記事)で「過激施術」を使い、質問票の表示名は変えない。今回のセラピストでは系統の行に特記をつないで料金の合計を出し、出勤確認は上旬・中旬・下旬までにぼかす。「有料部分の内容」の項目の整理は、本人が選ばなかったため変えていない。

総評の扱いは、本人が記事の型ごとに分けて決めた。体験内容起点(通常版)では良かった点を中心に書き、残念ポイントは短くしてリピート意向は書かない。最後の加減は本人がボードで直す。セラピスト起点(名前公開版)では、これまでどおり良い点も残念な点も正直に書く。

手直しの記録：本人が直した箇所を文体の調整に使えるようにした。ボードで素の文章を保存すると、保存前の文章(base)と直した文章(edit)を、その版のフォルダにある `.history` に残す(`scripts/article-history.mjs`)。base を残すのは、ファイルに最後の履歴と違う文章があったとき、つまり Claude が書いた文章のときだけである。`npm run article-edits` では、最新の base と今の原稿で異なる行を記事ごとに並べる。`data/` は Git の管理外なので、履歴はこのPCの中だけに置かれる。記事5は保存前の版が残っていなかったため、同日のセッション記録から生成時の原稿を復元して base とした。

同日追記：本人の指示で、「過激施術」への改名を記事だけでなくPJ全体に広げた。質問票、ボード、回答の取り込み画面の表示名も「過激施術」にした(`src/types.ts` の `RATING_LABELS`)。保存データのキー `ratings.ero` は、既存の回答JSONとスキーマとの互換のため変えていない。上の「質問票の表示名は変えない」は、この追記で置き換わる。

同日追記：本人が記事5の表記をそろえた際、締めの定型「皆さまのご武運をお祈りいたします!」の感嘆符を全角の「！」にすると決めた。生成プロンプト(`src/prompt/style-profile.ts`、`src/prompt/build-prompt.ts`)、マークアップの依頼(`src/prompt/markup-prompt.ts`)、記事テンプレート、文体プロファイルの定型を変えた。

## 更新方法

新しいユーザー指示で原案が変わった場合は、元の記述を消さず、変更した範囲、日付、発言または出典、現在の扱いを追記する。エージェントの提案を記録するときは提案と明記し、ユーザーが了承する前に確定要件へ移さない。

実回答を使った作業結果は、内容ではなく実施・未実施と確認範囲だけを残す。文書の移植完了、アプリの実装完了、記事の完成、本人による投稿完了は分けて更新する。
