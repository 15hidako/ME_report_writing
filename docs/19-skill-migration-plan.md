# 記事のルールをskillへ移す作業計画

作成日：2026-11-14
基準コミット：`1f01621`
読み手：実装を担当するエージェントと、承認する本人

PCの記事ボードが出す記事プロンプトには、文体、wakust規約、記事構成、装飾の部品、訪問データが毎回すべて入っている。PCでは Claude Code が記事を書くので、毎回同じルールはプロジェクトのskillに置き、ボードは記事ごとに変わる部分だけを依頼文として渡す。この文書はその作業を、1つずつ着手できる単位(WP)に分けたものである。

## 1. 範囲

対象は、ボード(`start.bat` で開くPC版)から出す次の2つ。

- 単体記事と再訪記事のプロンプト(`src/board/main.ts` の `copyArticlePrompt`)
- マークアップの依頼(同じく `buildMarkupPrompt` を呼ぶ箇所)

入力画面(公開版、スマホ)のプロンプトは変えない。スマホから Claude のアプリやWebへ貼る経路は元の設計([14-claude-requirements.md](14-claude-requirements.md))であり、そこではskillを使えないため、今の全文プロンプトを出し続ける。カタログ記事とまとめ記事のプロンプトも今回は変えない。まとめはボードからも出せるが、使う回数が少ないので後に回す。

## 2. 決めたこと

### ルールの原本は `src/prompt/` に残す

入力画面では全文プロンプトを出し続けるため、ルールの原本は今の TS に置いたままにする。SKILL.md は TS から生成し、手では書かない。同じルールを2か所に手で書くと、片方だけ直す事故が起きる。`style-profile.ts` の冒頭にある「docs側を更新したらここも同期すること」は、すでにその状態になっている例である。

SKILL.md の生成と更新漏れの検出には vitest の `toMatchFileSnapshot` を使う。SKILL.md が TS とずれていれば `npm test` が失敗するので、`npx vitest run -u` で書き直す。依存は増やさない。

### 訪問データは依頼文に載せる

Claude Code に `data/answers/` の JSON を直接読ませる形は採らない。回答は取り込んだあとに入力画面やボードで直されることがあり、直した内容はブラウザの保存領域にしかない。ファイルを読ませると、直す前の回答で記事を書くことになる。依頼文には今と同じく `serializeRecord` の出力を入れる。短くなるのはルールの部分で、データの量は変わらない。

### 記事ごとに計算する値はコードで決める

次の値は今と同じくコードで決め、依頼文に入れる。skillには書かない。

- タイトル先頭の【エリア｜○月出勤確認】(`titleLead`)
- 出勤確認を旬にぼかした行(`listingCheckLine`)
- 店舗情報の確認の節(`articleLookupSection`)
- 再訪の初回記事URLと初回の訪問データ
- タグ候補、販売ポイント案、保存先のパス

出勤確認のぼかしは、セラピストを絞り込ませないための処理である。モデルの判断には回さない。

### 販売型で変わる行は依頼文に入れる

体験内容起点とセラピスト起点で変わるのは、名前の開示規則、タイトルの規則、構成の5行(導入、今回のセラピスト、有料部分の内容、店舗・セラピスト情報、総評)である。両方をskillに載せて選ばせる形も考えたが、採らない。U-25 では販売型を取り違えた記事が一度できている。選んだ型の行だけを依頼文に入れ、skillには型によらないルールだけを置く。

### skillは2つに分ける

- `me-article`：記事を素の文章で書き、原稿4ファイルを保存する
- `me-markup`：本人が直した素の文章を、言葉を変えずにHTMLにする

マークアップでは文章を一切変えさせない。そこへ「語り手の反応を書く」などの執筆ルールを読み込ませると、言葉を足す余地が生まれる。だから分ける。

### 呼び出し方

依頼文の1行目を `/me-article` (マークアップは `/me-markup`)にする。Code タブに複数行の依頼文を貼ったとき、skillが起動して残りの行が渡るかはWP4で確かめる。うまくいかなければ、1行目を「me-article スキルを読んでから、次の記事を書く」に替える。

## 3. 移行後の依頼文

記事の依頼文は、上から次の順に並べる。

1. `/me-article`
2. 販売型(例：販売型：セラピスト起点。保存先は `names/`)
3. 名前の開示規則とタイトルの規則(販売型ごとの1〜2行)
4. 構成の5行(販売型ごと)と出勤確認の行
5. 店舗情報の確認の節(記録がある場合だけ)
6. 再訪の場合は初回記事URLと初回の訪問データ
7. タグ候補、販売ポイント案
8. 保存先の4ファイル
9. 訪問データ

マークアップの依頼文は、`/me-markup` に加えて、素の文章とHTMLの保存先のパス2組だけになる。

## 4. 作業

### WP1 生成をルールの節と記事ごとの値に分ける

触るファイル：`src/prompt/build-prompt.ts`、`src/prompt/style-profile.ts`、`src/prompt/markup-prompt.ts`

- 全文プロンプトを作っている文字列を、型によらないルールの節(前提、文体、規約の共通部分、構成の共通行、出力形式、素の文章の記法、装飾)と、記事ごとの値を返す関数に分ける。全文プロンプトは今と同じ順に並べ直して作る。
- 完了条件：入力画面の全文プロンプトが1文字も変わらない。既存の `build-prompt.test.ts` と `markup-prompt.test.ts` を変えずに通す。

### WP2 SKILL.md を生成する

触るファイル：`src/prompt/skill-files.test.ts`(新規)、`.claude/skills/me-article/SKILL.md`、`.claude/skills/me-markup/SKILL.md`

- WP1 の節を並べて SKILL.md を作り、`toMatchFileSnapshot` で比べる。
- `me-article` には、原稿を `data/articles/` の保存先へ書くこと、クライマックスの素材が足りないときの「⚠」の一言、記録にない描写を作らないことを含める。
- `me-markup` には、文字の並びが素の文章と一致するか確かめて報告する手順を含める。
- `.claude/` は `.gitignore` の対象外なので、SKILL.md はコミットされる。実回答や原稿は含めない。
- 完了条件：`npm test` が通り、TS のルールを1文字変えると SKILL.md の比較で失敗する。

### WP3 ボードの依頼文を差し替える

触るファイル：`src/prompt/article-prompt.ts`、`src/prompt/markup-prompt.ts`、`src/board/main.ts`

- `buildArticleBrief` と `buildMarkupBrief` を足し、ボードのコピーだけをこれに切り替える。入力画面(`src/main.ts`)は `buildArticlePrompt` のままにする。
- 完了条件：依頼文にルールの節の文が入っていないことと、販売型、タイトルの規則、出勤確認の行、保存先、訪問データが入っていることをテストで確かめる。販売型ごとに、依頼文と SKILL.md を合わせると全文プロンプトのルールがすべて含まれることもテストで確かめる。

### WP4 実際に書かせて確かめる

- ボードから、体験内容起点、セラピスト起点、再訪を1件ずつ依頼し、Code タブで書かせる。記事ごとに新しい会話で依頼する。前の記事の販売型が混ざるのを避けるためである。
- 同じ回答を旧プロンプトで書いた原稿と並べ、構成、タイトル、名前を出す範囲、出勤確認の時期が同じかを本人が確かめる。文章の出来は毎回揺れるので比べない。
- 原稿は `data/` の中だけで扱い、リポジトリにも外部にも出さない。

### WP5 要件文書を更新する

触るファイル：`docs/14-claude-requirements.md`、`docs/15-requirements-history.md`

- WP4 で本人が確かめたあとに行う。docs/14 の経路の段落に追記し、docs/15 に U-26 として経緯を書く。ボードからの経路だけでskillを使い、公開版は全文プロンプトのままであることを明記する。

## 5. 変えないもの

- ルールの文面。この作業は置き場所を変えるだけで、文体や規約の中身は変えない。
- 入力画面の全文プロンプト。
- 原稿フォルダの形式(`<通し番号4桁>-<回答ID>/standard|names/`)と、ボードの段階(`prompted` など)。

## 6. 残る心配

- skillが読み込まれないまま記事が書かれること。そうなると文体や規約の抜けた記事になる。WP4 で起動を確かめ、`me-article` の手順の最初に「原稿の前に、使う販売型と保存先を一言で確かめる」を置いて、読み込まれたかを本人が見分けられるようにする。
- ルールを直したのに SKILL.md を書き直し忘れること。これは WP2 のテストで防げる。
